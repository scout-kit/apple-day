For developers

Deploying

One Firebase project per group. It is the only boundary that is actually enforced.

One project per group

Several groups can run this, and each gets its own Firebase project: its own database, its own roster, its own hosting. Nothing is shared, so there is no query that could accidentally cross between them and no rule that has to be right for it not to.

The Firebase configuration is baked into the built files, which means one build belongs to exactly one project. Reusing a build across projects points one group's site at another group's data — and it looks entirely normal while it does it.

So the build and the deploy take the same name, from one command, and neither can be run without it: 

make deploy GROUP=<alias>

That runs every check first — typecheck, both test suites — then builds for that group and deploys hosting and rules together.

Aliases and configuration

An alias is a short name for a project, listed in .firebaserc. Each one needs a matching .env.<alias> holding that project's Firebase configuration and the address its volunteer links should point at.

Neither file is committed: they describe one installation rather than the app. Copy .firebaserc.example and .env.example and fill them in. The deploy refuses to run if either is missing, rather than quietly building with whatever configuration it found. 

make deploy-rules GROUP=<alias>   # rules and indexes only
make deploy-all                   # every alias, one at a time
make verify                       # every check, without building

Setting up a new project

  1. Create the Firebase project and add a web app.
  2. Create the Firestore database. Pick the region carefully — it is permanent. For a Canadian group, northamerica-northeast2.
  3. Enable Google sign-in under Authentication.
  4. Copy the web configuration into .env.<alias>, add the alias to .firebaserc, and set the public address volunteer links will use.
  5. Deploy.
  6. Grant the first admin by hand — see below.

The first account

A fresh deployment has an empty database and nobody on the roster, so the first person to sign in is refused. There is no way in that the app itself could offer, and offering one would be a hole in it.

  1. Sign in to the deployed app with the account that should be the first admin. You will be told you have no access; copy the account id it shows.
  2. In the Firebase console, under Firestore, create a collection admins with a document whose id is that account id, holding email (the address) and addedAt (0).
  3. The app notices on its own — the refused screen becomes the app, without signing in again.

Everybody after that is invited from the Access screen. This is the only step that ever needs the console.

Sending email

Reminders go through an organizer's own Gmail using OAuth in the browser, because the free tier has no server-side functions to send from.

In the Google Cloud console, on the same project: enable the Gmail API, then create an OAuth client of type "Web application" with your hosting address listed as an authorized origin. Leave the consent screen on External and in Testing, and add each organizer who will send as a test user. Sending mail is a restricted scope, so publishing the app would require a security assessment — Testing needs none.

On a Google Workspace domain, publish the app internally instead and consent stops expiring.

If none of that is set up, reminders still work: they come out as a file for whatever mailing tool the group already uses.
