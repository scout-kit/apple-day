For developers

Deploying

One Firebase project per group. It is the only boundary that is actually enforced.

One project per group

Several groups can run this, and each gets its own Firebase project: its own database, its own roster, its own hosting. Nothing is shared, so there is no query that could accidentally cross between them and no rule that has to be right for it not to.

The Firebase configuration is baked into the built files, which means one build belongs to exactly one project. Reusing a build across projects points one group's site at another group's data — and it looks entirely normal while it does it.

So the build and the deploy take the same name, from one command, and neither can be run without it: 

make deploy GROUP=<alias>

That runs every check first — typecheck, both test suites — then builds for that group and deploys hosting and rules together.

The other deploy commands

make deploy-rules GROUP=<alias>   # rules and indexes only, no build
make deploy-all                   # every alias in .firebaserc, one at a time
make verify                       # every check, without building or deploying

Setting up a new project

Once through, per group. Every step says where to click, because the Firebase console moves things around and half of these live two levels down a menu.

1. Create the Firebase project

  1. Go to console.firebase.google.com and press Create a project.
  2. Name it. The console turns that into a project id — often with digits on the end if the name is taken. Note the id, not the name: it is what goes in .firebaserc and .env.
  3. Google Analytics is not used. Turn it off or leave it; it makes no difference.

2. Add a web app to the project

A project has no configuration until an app is registered in it. This is the step that produces the values the app needs, and it is easy to miss because nothing prompts for it.

  1. On the project overview page, find the row of platform icons under the project name and press the web one — </>. If you have left that page: gear icon (top left, beside Project Overview) → Project settings → General, then scroll to Your apps.
  2. Give it a nickname — yours only, it appears nowhere.
  3. Do not tick "Also set up Firebase Hosting" here. The deploy does hosting itself, from the CLI.
  4. Press Register app. The next screen shows a firebaseConfig block. Leave it open — step 5 needs it.

3. Create the Firestore database

  1. In the left sidebar, under Build, choose Firestore Database.
  2. Press Create database.
  3. Pick the location carefully — it cannot be changed afterwards. For a Canadian group, northamerica-northeast2 (Toronto).
  4. Start in production mode — locked down. The deploy uploads the real rules, and starting locked means there is no window where the database is open to the world.

4. Turn on Google sign-in

Two levels down, and the provider is a tab of its own — which is why this one is easy to think you have done.

  1. Left sidebar, under Build, choose Authentication.
  2. Press Get started if it is a new project.
  3. Choose the Sign-in method tab — not Users, not Settings.
  4. In the provider list press Google, toggle Enable, pick a support email, and Save.
  5. Still in Authentication, open the Settings tab → Authorized domains. Your hosting domains (<project-id>.web.app and <project-id>.firebaseapp.com) are usually there already. If a popup opens and closes immediately later on, this is the first thing to check.

5. Write the two local files

Neither is committed — they describe one installation. Both have a template beside them, and both are dotfiles, so ls -a rather than Finder.

.firebaserc — which project an alias means:

cp .firebaserc.example .firebaserc
{
  "projects": {
    "default": "apple-day-local",
    "waterloo": "your-project-id-here"
  }
}

Leave default alone — it is the emulator, not a real project. Add one line per group: the alias on the left is what you type after GROUP=, the project id on the right is what step 1 produced.

.env.<alias> — the app's own settings. The file name must match the alias exactly: alias waterloo needs .env.waterloo.

cp .env.example .env.waterloo

There is no copy-and-paste of the whole firebaseConfig block. Four of its values are wanted, under different names. From step 2's screen — or gear icon → Project settings → General → Your apps → SDK setup and configuration → Config:

From firebaseConfigInto .env.<alias>
apiKeyVITE_FIREBASE_API_KEY
authDomainVITE_FIREBASE_AUTH_DOMAIN
projectIdVITE_FIREBASE_PROJECT_ID
appIdVITE_FIREBASE_APP_ID
storageBucketnot used — no Cloud Storage
messagingSenderIdnot used — no push
measurementIdnot used — no analytics

Plus one the console does not give you:

SettingValue
VITE_PUBLIC_ORIGIN where the site will live, e.g. https://your-project-id.web.app — no trailing slash

Quotes around the values are optional; both forms load identically. Do not put VITE_USE_EMULATOR in this file — it would build a public site that talks to a laptop. The deploy refuses if it finds one, and refuses if any of the four above is blank, because a blank one becomes an empty string in the built files and every sign-in then fails with api-key-not-valid.

6. Deploy

npx firebase login          # once per machine
make deploy GROUP=waterloo

This runs every check first, builds against .env.waterloo, then uploads hosting, the rules and the indexes together.

7. Let the first admin in

A fresh project has nobody on the roster, so the first person to sign in is refused — and the app cannot offer a way past that, because anything it offered would be a way in for everybody. So this one step happens in the console, which the rules do not bind.

What you create is an invitation, not a roster entry. That is not a detail: an invitation needs no Firebase account to exist yet. A roster entry is keyed by an account id, and there is no way to get one — signing in without access deletes the account it just made, and the rules forbid an account writing its own roster entry, which is what stops anybody promoting themselves.

Run this to get the exact values to type:

ORIGIN=https://your-project.web.app make bootstrap-admin

It only prints. Nothing here reaches your project, so there is no service-account key to download and no credentials to leave on a laptop. Add TIER=organizer for the lesser tier.

  1. Firebase console → left sidebar Build → Firestore Database → Start collection.
  2. Collection ID: invites.
  3. Document ID: paste the code it printed. Not auto-ID — the code is the document id, and the link will not find it otherwise.
  4. Add the two fields exactly as printed:
    • level — string — admin
    • invitedAt — number — the long number it printed (the time in milliseconds; it is what makes the link expire)
  5. Save.
  6. Open the /join/… link it printed and sign in with whichever Google account should be the first admin. Any account will do — it does not have to match any particular address.

The invitation is spent as you use it, so that document disappears on its own. Nothing to go back and tidy up, and no link left working afterwards.

If it says the invitation cannot be used

Nearly always one of three things: the document id has a stray space or a changed character, invitedAt was saved as a string rather than a number, or the collection is named invite. The page reads the invitation before asking you to sign in, so you find out before handing over an account.

Everybody after that gets an invitation link from the Access screen, which is the only route the app itself offers. make admin does a similar job but only against the local emulator — it cannot touch a deployed project.

Getting back in later

The same step, and it is worth knowing before you need it. If every admin loses access — an account closed, somebody removed by mistake, a person who has left — nobody can make an invitation from inside the app any more. Run make bootstrap-admin again, type the document again, and you are back in. Anybody with console access to the project can do this, which is also why console access is worth guarding: it is admin access, one step removed.

Sending email, if you want reminders

Optional. Without it the reminder screen still works and hands you a file for whatever mailing tool the group already uses; this is what lets it send from an organizer's own Gmail instead.

All of it happens in the Google Cloud console, not the Firebase one. They are the same project seen two ways, which is the part that catches people out — Firebase projects are Cloud projects, so nothing new is created here.

1. Enable the Gmail API

  1. Go to console.cloud.google.com.
  2. Check the project picker at the top and choose the same project. Landing in the wrong one and enabling things there is the commonest wasted hour.
  3. Left sidebar → APIs & Services → Library.
  4. Search Gmail API, open it, press Enable.

For the signup-form button, enable Google Forms API the same way while you are here.

2. Set up the consent screen

  1. APIs & Services → OAuth consent screen.
  2. Choose External. Internal is only offered on a Workspace domain — if you have one, take it, and consent then stops expiring.
  3. Fill in an app name and a support email. Nothing else is needed.
  4. Leave the publishing status as Testing. Sending mail is a restricted scope, and publishing it would mean a Google security assessment. Testing needs none.
  5. Under Test users, add every organizer who will send. Only those addresses can grant permission — this is the step that is easy to skip and produces a refusal that reads like a bug.

3. Create the OAuth client

  1. APIs & Services → Credentials → Create credentials → OAuth client ID.
  2. Application type: Web application.
  3. Under Authorized JavaScript origins add where the site is served from, with no path and no trailing slash: https://your-project-id.web.app. Add http://localhost:5173 too if you want to try it locally.
  4. Leave Authorized redirect URIs empty. This flow does not use one.
  5. Press Create and copy the Client ID — it ends .apps.googleusercontent.com. The client secret is not used and can be ignored.

4. Put it in the env file

From the Cloud consoleInto .env.<alias>
OAuth Client ID VITE_GOOGLE_CLIENT_ID
Client secret not used — a browser cannot keep one

Then deploy again, since this is baked in at build time like the rest: 

make deploy GROUP=<alias>

A client id is not a secret. What protects the account is the consent screen and the origins allowlist above, which is why it is safe in a built file at all.
