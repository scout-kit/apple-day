For developers

Development

Everything runs against the Firebase emulator. No Firebase project, no billing account, no cloud anything.

Prerequisites

Node 20 or later, and a JDK 11 or later — the Firestore emulator needs Java.

make doctor    # checks both, and says which is missing

Getting going

make up        # installs, starts the emulator, seeds it, serves the app

Then let yourself in:

make admin        # prints an invitation link — open it and sign in
make organizer    # the same, one tier down

Do this before signing in, not after. Signing in with no invitation gets you nothing: the account it creates is deleted straight away, which is what stops a real project filling up with strangers who pressed the button once. So the link comes first, and any Google account will do — it does not have to be an address anybody recognises.

Once you are in, make admin promotes instead of inviting, which is how you move an organizer up a tier.

make down stops everything. Access is part of the emulator snapshot, so it survives a restart and you only do this once.

Seeing the first-run experience

A brand-new deployment has no data and nobody on the roster, and that path is easy to break without noticing. To walk it: 

make firstrun        # empty emulator on its own ports, app at :5174
make firstrun-admin  # prints an invitation link for the sandbox
make firstrun-down

This is a whole second emulator, not another project id inside the one you work in. Firestore keeps projects apart, but the auth emulator does not — it answers every request from one set of accounts — so a "sandbox project" sharing an emulator would create its test users in the data you actually care about.

Layout

src/domain/     pure logic, no Firebase imports —
                types, slots, metrics, validation, importer, publishing
src/lib/        Firestore, auth, mail, QR, CSV — everything facing outward
src/ui/         screens and components
firestore.rules the entire authorization layer
test/           unit and render tests; test/rules/ needs the emulator
scripts/        workbook extraction (Python, stdlib only) and emulator seeding

src/domain has no Firebase dependency, so the calculations run in milliseconds and can be tested without a browser or a network. domain/publishing.ts lives there specifically because it decides what a volunteer is handed: the pass is the only thing reachable without an account, so a bug in it is a privacy problem rather than a display glitch.

Tests

There is a regression suite built from a real year's results, holding the dollar figures and dropping the names. It asserts the app reproduces the source workbook's totals where the workbook was right, and deliberately diverges where it was wrong. Those divergences are the point, so the tests name them:

Workbook saidCorrectWhy
One shop ranked twice, $177.88/hr and $165.46/hr One row, $1,526.41 The two day sheets spelled the name differently; the totals grouped by string
$86.55/hr, rank 4 of 12 Unrankable, listed as an anomaly IF(F17>0, E17/F17, E17) fell back to the raw total when hours were 0
Friday: 3 hours 4 person-hours COUNTA counted filled cells; one cell held two siblings
Saturday: 25 person-hours 56 The hours sheet scanned five of eight slots
Reconciliation "balanced" Friday short $86.55 A card total and bushel sales were summed into one column

Referencing everything by id rather than by display string is what removes most of that class of defect outright.

Notes

The hosting emulator sits on port 5050 rather than Firebase's default 5000, because macOS ControlCenter holds 5000. Development does not use it — Vite serves the app.

Source workbooks contain minors' names and parent contact details. The repository excludes the workbook itself, any exported responses, and the generated location list. Nothing derived from a real roster belongs in version control.
